# MR2 Reactive LEDs — Project Status

Reactive LED lighting controller (ESP32-C3 + MPU6050 + WS2812B) built and installed in a 1992 Toyota MR2 SW20. See [README.md](README.md) for what the system does.

## Core Project Complete

All physical installation is **complete** — control box, accelerometer, rotary encoder, and both LED strips are mounted in their final positions, running on real vehicle power (fused 12V from the cigarette lighter circuit). Rotary encoder brightness adjustment and LED strip output were confirmed working correctly in the car at this initial installation. Hardware/PCB work is done, including a GPIO4 fault on the first assembled board that was resolved by swapping to a spare PCB (root cause: damaged GPIO4 on that specific ESP32-C3 module, not a design fault).

The originally specified buck converter was swapped for a repurposed USB charger module after it caused intermittent cold-boot failures (likely an unclean voltage rise affecting ESP32-C3 strapping pins on boot). The replacement has since been cold-boot tested repeatedly with no recurrence — **confirmed fixed**.

**`v2.3`** was confirmed on real driving to work "almost perfectly" — `accelerationResponseG` tuned to `0.12` so higher gears reliably reach true orange, and Modes 1–4 fixed (via code review, before that drive) to actually track that same tuning instead of a stale hardcoded threshold. But it also surfaced a **new issue**, not present on earlier versions: flickering between red (braking) and blue (idle) while going downhill, with no braking input needed at all.

That flicker was traced to **v2.1 → v2.2**, not to v2.3's own changes: v2.2 slowed `gravitySmoothing` and made `baselineDynamicReentryThreshold` more sensitive, both specifically to stop sustained acceleration fading too early — but the same `gravitySmoothing` tracker also governs how fast a downhill grade gets absorbed into the baseline, so the fix for one problem quietly created another. It was initially assumed to be an inherent, unfixable accelerometer-only limitation; it wasn't.

**`v2.4.0`** attempted the fix by splitting `gravitySmoothing` by direction on the forward axis — the slow rate stays for accelerating (so the acceleration-hold fix is untouched), while the original fast v2.1 rate is restored for braking/downhill (which share a sign on the forward axis). **Drive-tested and found to make no difference at all** — downhill flicker unchanged, uphill/flat unchanged (both were already fine, so that's not evidence of success). Root cause: a hill pitch shifts gravity on the forward axis (X) *and* the vertical axis (Z) at once, since both are involved in the same rotation — v2.4.0 only made `gravityX` direction-aware, and `gravityZ`'s unchanged slow rate kept the combined gating signal (which sums all three axes) elevated regardless, so the baseline never settled any faster than on v2.3.

**`v2.4.1` is the final firmware version, confirmed on real driving.** It extends the same direction-aware rate to `gravityZ` as well (same forward-axis direction flag; `gravityY`, the lateral/cornering axis, is untouched) — this directly targeted the flicker without the blunt trade-offs considered earlier (e.g. dulling `brakingDeadZone` globally), and the next drive confirmed it worked: **the downhill flicker is gone**, acceleration-hold and braking both feel unchanged from v2.2/v2.3. `baselineDynamicReentryThreshold` (the fallback if this hadn't worked) is no longer a live concern.

**The core reactive-LED project is finished.** Two known issues remain, deliberately left unfixed — accepted, permanent trade-offs, not bugs to chase:
- USB power backfeeds enough current to power the car radio when connected with the key off (no reverse-blocking diode on the charger module). Not a safety/drain issue since it doesn't cross the ignition switch. Rule: never connect USB and vehicle power at the same time.
- Minor audible noise through the speakers when LED brightness changes — typical WS2812B PWM noise, barely noticeable.

**Active project work has moved on to the audio-reactive LED addition below.**

## Audio-Reactive LED Addition (Active — Current Focus)

A new, optional mode layered on top of the completed core project above: LEDs also react to music from the car radio, via an RCA tap → conditioning circuit → spare ADC pin (`GPIO1` on the production ESP32-C3). Independent of the v2.x firmware — doesn't touch or depend on it. Full plan: [docs/audio-reactive-led-plan.md](docs/audio-reactive-led-plan.md).

**Phase 1 (GitHub/bench-test sketch setup): complete.** Plan doc and its four circuit images committed, `firmware/tests/04_audio_reactive_test/` bench-test sketch added (a spare ESP32-C3 module — not the ESP32-C3 installed in the car), `hardware/audio-breakout.md` added, and a new build-log section tracking this separately from the numbered core-project Stages.

Design updated after the initial plan: D1 (rectifier diode) is a 1N4007, not the originally-planned 1N4148, based on what was on hand — fine here since the smoothing capacitor already makes this a hundreds-of-milliseconds envelope, not audio-frequency work. The testing circuit sums stereo L/R via R1/R2 from a 3.5mm breakout cable, mirroring the production circuit's RCA summing (in principle — see the mono note below), and now also has a monitoring speaker tapped in so audio content can be heard while tuning. **Testing board also changed**, from a generic full ESP32 dev board to a spare ESP32-C3 module — since that's the same chip as production, the audio ADC pin (`GPIO1`) is now identical on both test and production, so Phase 2 tuning carries straight into Phase 4 with no pin remapping (LED data uses `GPIO7` on the test board, arbitrary/free).

**Phase 2 (bench-test): Stage A complete and validated.** Conditioning circuit breadboarded and confirmed responding correctly to real music. Firmware rewritten from simple whole-strip brightness to a proper bar-graph audio visualizer (growing/shrinking LED bar with a bouncing peak-hold marker — fast attack, slow gravity-fall release) in `firmware/tests/04_audio_reactive_test/`. `audioFloor`/`audioCeiling` calibrated from real Serial readings to `900`/`1300` (idle ~950, loud peaks ~1200). Real-radio validation (originally Stage B) still moved to Phase 3 — the car's RCA wiring isn't practically accessible without opening up the already-installed system.

**Known issue, deferred:** the USB-C-to-3.5mm audio dongle used for bench testing occasionally distorts mid-playback, recovering after a reconnect — likely the monitoring speaker (8Ω) overloading the dongle's small onboard amp, which isn't rated to drive that low an impedance continuously. Not yet fixed since it hasn't blocked validation; a series resistor on the speaker tap or a powered speaker would address it.

**Car radio preout voltage confirmed from the Kenwood DPX-07MD's own service manual** (`B64-2858-00`, `仕様一覧`/specifications page): `プリアウトレベル (FM): 1.8V/10kΩ` — a rated preout of 1.8V RMS, ~2.55V peak. Replaces the earlier unconfirmed "~2–4V RMS" guess.

**Design corrections made during Stage A** (testing-circuit component names below; see the renumbering note further down for how these map to production designators):
- **R5 removed:** the originally-specified bias network (R5 10kΩ to 3.3V, R6 10kΩ to GND) set the envelope's resting voltage at 1.65V — but D1 only conducts once Node A exceeds that by its own forward-voltage drop, and Node A's realistic peak was nowhere near that. R5 removed entirely; R6 alone now returns Node B to GND (~0V resting point), the standard single-resistor diode-envelope-detector topology.
- **R3/R4 (the old divider) removed entirely, R1/R2 reduced 2.2kΩ → 470Ω**, found via live bench testing: breadboarding with the divider still in place showed the circuit completely dead, because the combined attenuation left too little signal for D1 to ever conduct. Removing the divider and reducing R1/R2 (still enough for channel isolation/short-protection) restored a real response.
- **A DC-blocking coupling capacitor + reference resistor — adopted for production** (renamed C4/R5 there, not part of the validated testing circuit — see below). A first attempt using two polarized electrolytics wired back-to-back (a common non-polarized-cap trick) failed and stayed failed even after reseating — root cause: that trick only tolerates brief, symmetric AC reverse-bias, not the *sustained* DC offset this needs to block, so one cap was under continuous reverse bias and degraded. **Must be a genuinely non-polarized capacitor** (ceramic or film, ~2.2–4.7µF) — needs sourcing, not currently on hand.

**Testing circuit is currently mono, not stereo:** the breakout cable's "white" wire turned out to have continuity with the shield — it's a second ground/drain wire on this cable, not a real left-channel conductor. Testing runs through the red wire/R2 only for now; R1 stays in the circuit but its input is unconnected.

**Phase 3: in progress — PCB remanufacture and firmware development.** Rather than a standalone breakout board, the audio circuit will be integrated directly into a new PCB revision (`v2`) — same EasyEDA → JLCPCB process as the original board. This phase now also covers writing the new firmware mode, once the board's been ordered — no need to wait idle for manufacturing/shipping. All circuit decisions are finalized:

- **D1 upgraded to a BAT85 Schottky diode for production** (testing circuit keeps its validated 1N4007). Lower forward voltage (~0.15–0.3V vs. ~0.3–0.6V) helps quiet passages register now that the coupling cap gives a genuinely clean near-0V baseline. Ordered.
- **Production designators renumbered**, since `v1`'s real board already uses `R1`/`R2` (330Ω) and `C1`/`C2` (1000µF/100nF) for other things. Production continues straight on from those: **R3/R4** (470Ω isolation), **R5** (4.7kΩ coupling reference — see correction below; informally "R7" in testing-only text), **R6** (10kΩ discharge, unchanged), **C3** (2.2µF smoothing), **C4** (coupling cap, non-polarized, 2.2µF, ordered). Full mapping is in `docs/audio-reactive-led-plan.md` and `hardware/audio-breakout.md`.
- **`J6_SWITCH` removed** — `v1`'s switch connector was never populated (just shorted instead), dropped for `v2`. New RCA input connector is **`J7`** (JST-XH 3-pin, matching the existing J2–J5 style).
- **Parts ordered**: non-polarized coupling capacitor (C4), BAT85 diode (D1), JST-XH 3-pin connector set (J7). Everything else needed was already on hand.
- **R5 corrected from 100kΩ to 4.7kΩ, found via Multisim simulation after Gerbers were already submitted.** The original 100kΩ spec only modelled C4/R5 as a simple AC high-pass filter (which it passes ~99.5% of signal, true in isolation) — missing a self-biasing effect where D1 pulling current from Node A on each peak forces Node A's *average* voltage down (since C4 blocks DC, that current has to balance against R5), eating into the peak voltage that ever reaches the diode. At 100kΩ, simulation confirmed only ~9% of the signal reaching Node A actually made it to Node B (~0.2V against the real 2.55V peak, not the ~2.2–2.4V originally assumed). 4.7kΩ was found by testing the R5/R6 self-bias trade-off against the R5/C4 bass-response trade-off together — Node B's voltage actually peaks around R5≈5–6kΩ and falls off below that, so lower isn't always better. Result: ~1.1–1.4V at Node B, a 5x+ improvement, using the same 2.2µF C4 already on hand — no new part needed. R5 is hand-soldered (same cheap-hand-swap list as R3/R4/C3/C4), so this doesn't require a re-fab — solder 4.7kΩ instead of the 100kΩ shown on the `v2` schematic. Full derivation in `docs/audio-reactive-led-plan.md`.

**`v2`'s EasyEDA schematic/layout is designed and verified, and the board has been ordered from JLCPCB** (Global Standard Direct Line shipping, 8–12 business days quoted — now in fabrication/shipping). Cloned from the `v1` project rather than editing it in place. DRC clean (0 errors). EasyEDA Standard has no separate ERC report like KiCad/EasyEDA Pro — schematic connectivity was instead verified directly from the exported schematic JSON (tracing wires/pins/junctions), confirming the Node S/A/B topology and GND net match the documented circuit exactly. That check also caught `J7`'s Front Left/Front Right RCA pins initially wired backwards (R3=Right/R4=Left) — fixed in EasyEDA and re-verified as R3=Left/R4=Right, matching the docs. Design files (Gerbers, EasyEDA BOM export, schematic + PCB JSON) are committed under `hardware/pcb/v2/{gerbers,bom,easyeda}/`; `v1`'s `easyeda/` folder was also retroactively completed with its own schematic JSON, which had been missing. The system BOM (`hardware/bom/MR2_Reactive_LEDs_System_BOM.xlsx`) now has a separate `Audio Addition` tab listing the new parts.

**PCB files are organised by revision**: `hardware/pcb/v1/{gerbers,bom,easyeda}/` (currently installed) and `hardware/pcb/v2/{gerbers,bom,easyeda}/` (designed, ordered, in fabrication/shipping) — mirrors how firmware versions are folder-organised. `hardware/audio-breakout.md` documents the now-superseded standalone-breakout circuit design (still accurate on the circuit itself, just not the "separate board" framing). **Phase 3 is PCB fabrication + bench assembly (no real radio involved) plus firmware development** — visual inspection, continuity, power-on testing for the board, same as `v1`'s original validation; the new firmware mode (`v4.0`) has been drafted and compiles clean, though bench-testing it against real audio is blocked until the conditioning circuit parts are available again (currently with the board). **Real-radio validation happens during Phase 4's install instead**, avoiding tapping the car's RCA wiring twice (once for an early bench check, again for permanent install); if `R3`/`R4`/`R5`/`C3`/`C4` need correcting at that point, that's a cheap hand-swap, not a re-fab.

**`v4.0` firmware drafted** in `firmware/mr2-reactive-leds/v4.0/`, branching from the final `v2.4.1` — a new major version line rather than a `v2.x` point release, to clearly distinguish the audio-reactive addition from the core motion-reactive line (`v2.x`) and the parked gyroscope experiment (`v3.x`). Mode 1 (previously a fixed purple theme) is replaced entirely by a bar-graph audio visualizer ported from the bench-test sketch: reads `GPIO1`, same attack/release envelope smoothing, cyan-to-orange colour snap with hysteresis (the flicker fix found on the bench sketch, carried over from the start), drawn identically on both strips. Bar length represents volume; LED brightness is a separate thing, capped by the same rotary-encoder `userBrightness` ceiling every other mode uses. The bench sketch's `Serial.availableForWrite()` fix was also applied to `v2.4.1`'s pre-existing Serial calls, which never had it. Compiles clean (0 errors, 0 warnings) against the real ESP32-C3 Super Mini target, verified with `arduino-cli`. **Not yet bench-tested against real audio** — the conditioning circuit parts are with the `v2` PCB, not available on the bench; `audioFloor`/`audioCeiling` remain Phase 2 placeholders (`900`/`1300`) needing retuning against the real radio.

**Phase 4 (install and test): not started**, depends on Phase 3. Tests, in order: the radio/speaker system still works after the RCA tap, then the original accelerometer-reactive system still works, then the new audio circuit against real radio (retuning `audioFloor`/`audioCeiling` as needed), then the `v4.0` firmware driving the real strips.
